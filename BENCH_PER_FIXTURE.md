# Per-fixture best-config benchmark

This document records, for every benchmark fixture, the **retrieval configuration that
maximizes that fixture's held-out quality** — measured, not asserted. It is the audit
trail for the README "best achievable" table and for the `<best_configuration>` blocks
in `prompts/frameworks/*.md`. Every number here is produced by the unmodified ranking
engine via `bench/cell.mjs` / `bench/repeat-score.mjs` and stored under `bench/results/`.

## What "best config" means here

The winner for a fixture is selected on the **held-out** split (the ~20–25% of queries
authored fresh and never used to tune ranking), in this order:

1. **held-out success@5 (strict)** — at least one exactly-correct symbol in the top 5,
   no file-path fallback. This is the adoption signal.
2. tie → **held-out MRR (strict)**.
3. tie → **lowest cost**. A fixture whose cheap default already maxes held-out reports the
   *cheapest* config that reaches the ceiling — not a heavier config that merely ties.
   Cost order (cheap→expensive): `L1 < E0 < O0 < O0H < O0R < O0HR < O2 < O2H < R0 < O2HR < R1 < R2`.

Held-out splits are small (n=3 per fixture; symfony n=4). **A single query moves held-out
success@5 by 0.33.** Treat held-out numbers as directional, not precise — the tuning split
(larger n) is shown alongside for context. The winner is still chosen on held-out because
optimizing the tuning split alone is overfitting.

### Determinism and the 3× rule

HyDE and the LLM reranker run at generation temperature > 0, so they are **nondeterministic** —
a single "perfect" run can be a lucky draw (the prior Laravel investigation saw held-out
rank-1 swing {1.0, 0.333, 1.0} across three identical runs). Therefore:

- **Deterministic configs** (`L1`, `E0`, `O0`, `O2`, `R1`) are measured once — that single
  value is the true value.
- **Nondeterministic configs** (any with HyDE or rerank: `O0H`, `O0R`, `O0HR`, `O2H`, `R0`,
  `O2HR`, `R2`) are scored **3×** via `bench/repeat-score.mjs`. The reported metric is the
  **median** (stable) value; rank-1 is shown with its **min–max spread**.
- A nondeterministic config is **winner-eligible only if reproduced 3×**. A single-run
  HyDE/rerank cell is recorded as supplementary evidence (‡) but never crowned — a lucky
  draw must not become a documented "best config".

## Measurement protocol & environment

- **Cold, isolated builds.** `bench/cell.mjs` wipes `.graph-indexer/` before each build, so
  wall-time, peak RSS, and index size are comparable. Query-time configs (`*H`, `*R`, `*HR`,
  `R0`, `R2`) are scored on the already-built index of their base embed config (`--reuse`),
  so the expensive embed build runs once per (fixture, embed-model), not once per variant.
- **Ollama models present** in the measurement environment: `nomic-embed-text`,
  `qwen3-embedding:4b`, `qwen2.5-coder:7b` (rerank), `qwen2.5-coder:1.5b` (enrich + HyDE).
  `qwen3-embedding:0.6b` (the would-be `O1`) is **not pulled** → not run.
- **Build cost is the binding constraint.** `qwen3-embedding:4b` indexes at ~0.7–3 chunks/s,
  so a single `O2` build ranges from ~6 min (small fixtures) to ~80 min (rails, 7071 chunks);
  `R1` (enrichment) builds are ~2× that. The grid is therefore **focused**: heavy configs are
  measured where they can change the held-out winner; the 12 fixtures whose cheap config
  already saturates held-out success@5 = 1.00 are not rebuilt under the heavy stack (a heavier
  config cannot beat a 1.00 ceiling, and cost breaks the tie toward the cheap config). The
  pruning is recorded per fixture below.

### Fixture coverage in this pass

- **Full heavy grid (nomic-HyDE + qwen + enrichment):** laravel, symfony — no prior O2/R1 data
  and contested held-out; the full grid (incl. enrichment, to also check enrichment coverage).
- **nomic-HyDE + qwen (no enrichment rebuild):** spring, rust (existing single-run R1/R2 kept,
  flagged), nestjs, rails (rails R1/R2 **not run — ~2.5 h build is prohibitive**; nestjs

  nomic-HyDE family.
- **Cheap configs only (L1/E0/O0):** axios, fastapi, react, android, aspnet, css, cjson, nvm —
  cheap config already maxes held-out success@5; heavy builds pruned (documented).
- **express-ts: NOT MEASURED.** The suite exists (`test/suites/express-ts.mjs`) but its upstream
  fixture repo (`microsoft/TypeScript-Node-Starter`) now returns **HTTP 404** — Microsoft has
  removed/archived it, so the fixture cannot be checked out. It also has **no held-out split**

### What this means for adoption

- **Maxed by the cheap lexical default (L1 — no Ollama, no embeddings):** axios, express-js, fastapi, android, symfony, nvm. **6 fixtures** need nothing beyond the shipped default to hit their best held-out success@5.
- **Best with a cheap embedding channel (no LLM stack):** gin, react, django, rails, cjson (in-process **E0** — no Ollama daemon), aspnet, css (**O0** nomic — Ollama, sharpens rank-1 only; L1/E0 already max success@5). **7 fixtures.**
- **Genuinely benefit from the heavy stack (and by how much):** **nestjs** (O0HR, held s@5 0.67→1.00, **+0.33**), **rust** (R1 enrichment, 0.33→0.67, **+0.33**), **spring** (R0, 0.67→1.00, **+0.33**), **laravel** (O0HR, 0.67→1.00, **+0.33**), **alamofire** (embeddings 0.67→1.00; rerank sharpens rank-1→1.00). **5 fixtures.**

### Configs whose advertised benefit did NOT reproduce

- **qwen3-embedding:4b (O2) is never a sole winner.** It ties nomic at best and **regresses held success@5 on gin (1.00→0.67) and django**. The heavier embedder over-contributes on keyword queries and displaces exact-name hits — measured, not assumed. (On laravel, nomic+HyDE+rerank beats the qwen3 variant 1.00 vs 0.67.)
- **Rerank is double-edged, not a free win.** It lifts spring/laravel/alamofire, but **regresses rails held success@5 (0.67→0.33)** and **regresses express-js tuning rank-1 (0.67→0.57)** — the rerank tax on symbolic/JS queries. Do not enable it globally.
- **Enrichment helps only rust.** On **laravel** it does not move held success@5 (stays 0.67) and **drops the tuning split (0.82→0.45)** — consistent with the known core-chunk-selection coverage miscalibration (PageRank-by-file budget spent on Http controllers, starving Services/). Flagged here, not fixed (separate follow-up).

### The residual ceiling — hard queries no config solves

These are the honest intent→identifier gaps, stated as the ceiling rather than hidden:

- **symfony** — held 0.75/0.50 under *every* config (embeddings, HyDE, rerank, enrichment, qwen3). No channel closes the gap.
- **rails** — held success@5 capped at 0.67; no config exceeds it and rerank actively regresses it.
- **rust** — best held success@5 is 0.67 but **held rank-1 stays 0.00** — the right symbol reaches top-5, never the top.
- **cjson** — held rank-1 is **0.00 for every config** (the right *file* ranks top-5 but the exact symbol never rank-1 — a within-file ranking gap, addressable via `get_file_skeleton` + `get_chunk`).
- **django** — held rank-1 ceiling 0.33 (hard semantic ORM/view queries).
