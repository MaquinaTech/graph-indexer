## 1. Trajectory and token studies (2025–2026): where SWE agents spend tokens, turns and reasoning

### Takeaway
The 2026 literature agrees on four points. (i) Agentic coding cost is dominated by **re-sent input**, i.e. the cached prefix re-read on every turn, and not by new information. (ii) Cost is highly stochastic, up to 30x between runs of the same task, and does not track accuracy. (iii) Read-type actions are the biggest content category (~76% of tokens in one analysis), and ~26% of file reads are re-reads. (iv) Refinement and verification, not first-pass generation, is where multi-agent pipelines spend most. These match graph-indexer's measurements (half of cost after the first edit; prompt re-reading dominant).

### Cited Findings
- **Tokenomics (ChatDev, SDLC phases).** 30 software development tasks were traced in ChatDev. The iterative **Code Review stage consumes 59.4% of tokens on average**, and **input tokens are 53.9%** of consumption. The authors conclude that "the primary cost of agentic SE lies not in initial code generation but in automated refinement and verification." [abstract-verified] — [Tokenomics: Quantifying Where Tokens Are Used in Agentic SE, arXiv 2601.14470](https://arxiv.org/abs/2601.14470). Code/license: not verified. *Usable in graph-indexer?* Yes, as framing: it supports targeting the post-edit and verification phase rather than localization.
- **"How Do AI Agents Spend Your Money?" (Microsoft Research / Stanford Digital Economy Lab, Apr 2026).** Trajectories of **8 frontier LLMs on SWE-bench Verified**. Agentic tasks consume **~1000x more tokens** than code reasoning or code chat, and **input tokens, not output, drive overall cost**. Runs on the same task differ **by up to 30x** in total tokens. **Accuracy often peaks at intermediate cost and saturates at higher cost**; higher spend often reflects unproductive exploration. Models asked to predict their own token cost before running reach only weak-to-moderate correlation and systematically **underestimate** it because of long-horizon context growth. [abstract-verified] — [arXiv 2604.22750](https://arxiv.org/abs/2604.22750); [MSR page](https://www.microsoft.com/en-us/research/publication/how-do-ai-agents-spend-your-money-analyzing-and-predicting-token-consumption-in-agentic-coding-tasks/). *Usable?* Yes, for evaluation: at 30x run-to-run variance, graph-indexer's A/B results (the 15% vs 55%) need several seeds per issue and paired comparisons.
- **Read operations dominate: 76.1% of tokens.** In SWE-Pruner's analysis of coding-agent trajectories, **read-type operations use 76.1% of tokens**, against execute 12.1% and edit 11.8%. The paper also notes that code retrieved in earlier rounds persists and accumulates across rounds. [snippet, body text] — [SWE-Pruner, arXiv 2601.16746](https://arxiv.org/abs/2601.16746).
- **Duplicate reads: 26%.** In CORVUS's empirical analysis, **26% of Claude Sonnet 4 file-read operations re-read files already read earlier**. Each re-read appends another full snapshot. Stale snapshots after edits cause reasoning errors and trigger still more re-reads. [snippet, body text] — [CORVUS, arXiv 2607.22711](https://arxiv.org/abs/2607.22711).
- **Prompt cache dominates the bill (Claude Code).** 2,908 provider-billed Claude Code runs across 103 tasks, 7 repositories and 3 models. **Prompt-cache traffic was ~87% of reconstructed four-component cost.** An arm that **removed 38% of estimated raw tool-output tokens had 6.8% *higher* paired cost**. The mechanism: when compression removes something the model later needs, it searches again, re-reads or takes extra diagnostic turns, and each added turn re-sends the whole prefix. [abstract-verified] — [Token Reduction Is Not Cost Reduction, arXiv 2607.12161](https://arxiv.org/abs/2607.12161) (July 2026; PointFive research). *Usable?* **This is the most directly relevant finding for graph-indexer.** It explains why "cleaner context (3x more lines in the changed functions)" did not lower cost. The metric to optimize is **turns x prefix size**, i.e. cache reads, not tokens per read.
- **Task-specification sensitivity.** Kimi K3 at 3 thinking-effort levels, 2,700 runs. Cutting a full task specification down to a bare user story **raises token spend by 29.7%**. Prompt sensitivity is **task-dependent, 13%–115%**. A single cheap probe run can price the whole specification-by-effort distribution on an unseen task to within 36%. [abstract-verified] — [Can your AI agent be cheaper?, arXiv 2608.25399](https://arxiv.org/abs/2608.25399). *Usable?* Yes. Precomputed "what to change and what done looks like" facts in the prompt (a compiled issue brief) are a plausible lever for up to ~30% of spend.
- **Overthinking in agentic SWE.** 4,018 trajectories from 19 LLMs on SWE-bench Verified. The paper names three patterns: **Analysis Paralysis, Rogue Actions, Premature Disengagement**. Higher overthinking scores correlate with lower resolve rate, and **reasoning models overthink more** than non-reasoning ones. Selecting the candidate with the lower overthinking score **improves performance by almost 30% and cuts compute cost by 43%**. [abstract-verified] — [The Danger of Overthinking, arXiv 2502.08235](https://arxiv.org/abs/2502.08235). *Usable?* Partly. Graph-indexer cannot change the model, but a hook could detect analysis-paralysis signatures (long reasoning with no tool call, or repeated reads of the same symbol) and inject a concrete next action.
- **Code cleanliness (Claude Code, 660 trials).** Minimal-pair repositories with the same behaviour but different static-analysis violations and cognitive complexity, 33 tasks across 6 pairs. **Pass rate unchanged (-0.9 pp)**. Cleaner code gave **input tokens -7.1%, output tokens -8.5%, reasoning characters -11.1%, file revisitations -33.8%**. [snippet, body text] — [Does Code Cleanliness Affect Coding Agents?, arXiv 2605.20049](https://arxiv.org/abs/2605.20049). *Usable?* Yes, as evidence that **representation quality moves reasoning and output modestly (~10%)**, and moves re-visits more (~34%).
- **Harness component ablation (Sept 2026).** 4 models on SWE-bench Verified and Terminal-Bench 2.1, 176 matched settings (5 context-management strategies, 4 context budgets, planning and action-space ablations). Findings: **context management extends trajectories without substantially changing agent behaviour and helps most under tight budgets**. **Planning "trims repeated verification in models that verify too long"** and keeps early-quitting models going. Structured tools help models with weak shell skills, while **bash-only lets capable models batch several edits in one call**. [abstract-verified] — [An Empirical Study of Harness Design for Coding Agents, arXiv 2609.20804](https://arxiv.org/abs/2609.20804). *Usable?* Yes. The post-edit phase (verification loops) responds to *planning/structure* interventions, not context interventions. This is a direct lever for graph-indexer's "half of cost after first edit" finding.
- **Thinking budget saturates.** Claude 4 Sonnet on SWE-bench Verified with 8k/16k/32k thinking budgets resolves **67.3% / 68.4% / 68.7%**, i.e. diminishing returns above 16k. [snippet, body text; appears to be from Confucius Code Agent, Meta] — [arXiv 2512.10398](https://arxiv.org/pdf/2512.10398). Not verified in context.
- **Localization is a cheap, separable stage.** On IssueLoc-Bench (499 SWE-bench-Verified-derived tasks plus 500 tasks from 153 other repos), lower-cost explorer models keep **~78–94% of reference Hit@3** and 73–92% of F1 while cutting **mean agent time by 41–88% and tokens by 84–95%**. [abstract-verified] — [Cost-Effective Repository Exploration for Agentic Issue Localization, arXiv 2608.29675](https://arxiv.org/abs/2608.29675) (AgenticDev '26).
- **Multi-file localization.** Naive file-system access can *degrade* localization through test-file over-prediction. **Forced multi-agent consultation does not measurably help and substantially raises token cost.** Documentation evolution is a latent dependency that no approach resolves. [abstract-verified] — [Exploration Structure in LLM Agents for Multi-File Change Localization, arXiv 2606.11976](https://arxiv.org/abs/2606.11976).

### Inferences
- For bug fixing on API models with prompt caching, cost ≈ Σ_turns (cached prefix x cache-read price) + output/reasoning. The two levers are **(a) fewer turns** and **(b) slower prefix growth**. Denser reads help only if they remove *future turns*. That is why graph-indexer's cleaner-context result showed no gain: precision inside the changed functions does not remove verification turns.
- Localization is now the *cheap* part (84–95% token savings are possible with small explorers), so the ~15% ceiling on bug fixing is plausibly just localization's share of total cost. The remaining ~85% is in reasoning, editing and verification loops.
- Run-to-run variance (up to 30x) means graph-indexer's measurements need ≥3 seeds per task and paired statistics before claiming small (±10–15%) effects.

### Gaps
- No study found gives a clean **per-phase split (localize / read / edit / test / verify)** of cost for Claude Code or Codex on SWE-bench Verified with cache-read accounting. The Tokenomics split is for ChatDev, a different SDLC pipeline. The MSR/Stanford paper likely has more breakdowns but the full text could not be accessed.
- The **reasoning-token share** of cost for current thinking models (Opus 4.x, GPT-5.x) in SWE agents is not reported in any abstract found.
- Cost-efficiency leaderboards (HAL, SWE-bench Pro/Scale, morphllm) were seen only as search results. They were not checked and are not included as evidence.

## 2. Observation and context reduction/management techniques with measured effects

### Takeaway
Simple, deterministic techniques work as well as or better than LLM summarization: **masking old observations (~50% cost cut), keeping one synced copy per file (CORVUS: 9–50% input, up to 37% fewer cycles), and pruning waste (AgentDiet: 21–36% cost)**. Line-level task-aware pruning (SWE-Pruner) also cuts output tokens and rounds (~40% / 18–35%). But token reduction that breaks cache prefixes or forces recovery turns can *raise* cost. Summaries can hide failure signals and lengthen trajectories.

### Cited Findings
- **Observation masking vs LLM summarization ("The Complexity Trap", JetBrains Research, NeurIPS 2025 DL4Code workshop).** SWE-agent on SWE-bench Verified, 5 model configurations, with initial evidence on OpenHands. Masking (older tool observations replaced by a placeholder, last M observations kept) **halves cost relative to the raw agent while matching, sometimes slightly exceeding, the LLM-summarization solve rate**. With Qwen3-Coder 480B, masking is **52% cheaper than raw and raises solve rate 53.8% → 54.8%**. LLM summarization causes **"trajectory elongation"**: summaries hide failure signals, so agents keep going in unproductive loops. A **hybrid** is 7% cheaper than masking and 11% cheaper than summarization. [abstract-verified + snippet] — [arXiv 2508.21433](https://arxiv.org/abs/2508.21433); code: [JetBrains-Research/the-complexity-trap](https://github.com/JetBrains-Research/the-complexity-trap) (license not verified). *Usable?* Only where graph-indexer controls the harness, since Claude Code hooks cannot rewrite past turns. Graph-indexer can instead **return outputs designed to be masked safely**: short, self-contained facts whose loss costs no re-read.
- **AgentDiet (FSE 2026).** Integrated into Trae Agent (Claude 4 Sonnet based). A reflection module, which can run on a cheaper LLM, removes **useless, redundant and expired** information from the trajectory. Results: **input tokens -39.9% to -59.7%**, **total computational cost -21.1% to -35.9%**, same resolve rate, on SWE-bench Verified and Multi-SWE-bench Flash with Claude 4 Sonnet and Gemini 2.5 Pro. [abstract-verified] — [arXiv 2509.23586](https://arxiv.org/abs/2509.23586); [ACM DOI 10.1145/3797084](https://doi.org/10.1145/3797084). Code/license: not verified. *Usable?* Only indirectly. The "expired" class, meaning file snapshots invalidated by edits, is something graph-indexer can **detect deterministically** because it knows which functions changed. It could tell the agent (or a CORVUS-like harness) which earlier reads are stale.
- **CORVUS (Jul 2026).** Replaces inline file reads with a `sync_file` tool that *registers* files. Before each reasoning cycle, a context-sync phase injects the **current** contents of every registered file, so there is at most one version per file. Results: **9–50% fewer average input tokens per task**, **15–32% shorter final prompts**, **up to 86% fewer duplicate reads** (22–86% across models), **up to 37% fewer reasoning cycles**, comparable pass rates. [abstract-verified + snippet] — [arXiv 2607.22711](https://arxiv.org/abs/2607.22711). Code/license: not verified. *Usable?* **High relevance.** This is a "live view" rather than an append-only log, and it attacks post-edit re-reads, the phase graph-indexer cannot currently reduce. A graph-indexer version would register **symbols** (functions/classes) rather than files, and refresh them from the incremental index after each edit. This needs harness control (an MCP server cannot inject into the prompt each turn). A partial version is possible through a hook that injects a "current state of your working set" block each turn, but that breaks cache prefixes. See §6.
- **SWE-Pruner (Jan 2026).** Middleware that intercepts file-reading commands (cat, grep). The agent states a goal hint, and a **0.6B skimmer (Qwen3-Reranker backbone plus CRF line head)** keeps the relevant lines while preserving structure. Mini-SWE-agent on SWE-bench Verified: with **Claude Sonnet 4.5, prompt tokens -38.7%, completion tokens -40.8%, total -39.2%, agent rounds -18.3%**; with **GLM-4.6, -44.2% / -44.0% / -43.6%, rounds -34.6%**. Overall 23–54% token reduction on agent tasks and up to 14.84x compression on single-turn LongCodeQA, with "minimal performance impact". [abstract-verified + snippet] — [arXiv 2601.16746](https://arxiv.org/abs/2601.16746); code: [Ayanami1314/swe-pruner](https://github.com/Ayanami1314/swe-pruner) (license not verified). *Usable?* **Yes, as a PostToolUse/MCP read filter.** This is notable because it cut **completion tokens** by ~40%, in line with fewer rounds. Graph-indexer could approximate the pruning with graph-based structural relevance instead of a neural skimmer (keep the target function, callees' signatures and relevant branches), or run the 0.6B skimmer locally.
- **ContextSniper (AntTrail, Jul 2026).** A memory layer between the agent and the repository: hybrid retrieval, an intention-aware gate on long outputs, and compact evidence packets, with the full source kept recoverable outside the prompt. Results: **Claude Code total tokens -38.9%, estimated cost -27.3%**; OpenClaw -51.5% tokens, -36.4% cost. **Resolution dropped slightly: Claude Code 32.0% → 30.0%, OpenClaw 26.0% → 24.0%.** [abstract-verified] — [arXiv 2607.01916](https://arxiv.org/abs/2607.01916); code: github.com/Calluking/ContextSniper (license not verified). *Usable?* Yes. It is architecturally close to graph-indexer and shows the typical trade-off: ~27% cost for about -2 pp resolve.
- **ACON (ICML 2026).** Optimizes compression guidelines in natural-language space using paired trajectories where full context succeeds and compressed context fails, then distills the compressor into smaller models, which keep 95% of teacher accuracy. **Peak tokens -26–54%**, up to 46% improvement for small LMs. Evaluated on AppWorld, OfficeBench and multi-objective QA, **not SWE**. [abstract-verified] — [arXiv 2510.00615](https://arxiv.org/abs/2510.00615). *Usable?* The method (failure-driven refinement of *what to keep*) could tune graph-indexer's output templates offline.
- **Anthropic context editing + memory tool.** In a **100-turn web-search evaluation**, context editing (auto-clearing stale tool results) **cut token consumption by 84%** and let agents finish workflows that would otherwise exhaust the context. Memory tool plus context editing gave **+39%** on an internal agentic-search eval, and context editing alone **+29%**. [vendor claim, not SWE-specific] — [Managing context on the Claude Developer Platform](https://claude.com/blog/context-management). *Usable?* Only through the API harness, not through an MCP server.
- **OpenHands condenser.** Without condensation, context grows quadratically; with it, linearly. The LLMSummarizingCondenser "reduces API costs by up to 2x with no degradation". A reported comparison: **condenser 200 vs baseline 203 resolved, and it cost ~$40 more because of lower prompt-cache use**, while latency held at ~8 s against 12–16 s at later iterations. [vendor blog/snippets; the "$40 more" figure is from a GitHub PR discussion, context not verified] — [OpenHands blog](https://www.openhands.dev/blog/openhands-context-condensensation-for-more-efficient-ai-agents); [PR #6597](https://github.com/OpenHands/OpenHands/pull/6597). *Usable?* It is a cautionary data point: **cache invalidation can cancel token savings**. This agrees with arXiv 2607.12161.
- **Code minification (TU Wien, 2025/2026).** Minifying source (shortening or removing non-essential lexical elements) in a state-in-context agent (DirectSolve) on SWE-bench Verified **cut input tokens by 42% but dropped resolve rate by 12 pp**. [abstract-verified] — [arXiv 2606.01326](https://arxiv.org/abs/2606.01326); [thesis](https://repositum.tuwien.at/handle/20.500.12708/224666). *Usable?* It is a **negative** signal: lossy lexical compression of code hurts accuracy. Identifiers and comments carry meaning the model relies on.
- **LongCodeZip (ASE 2025).** Two-stage compression by conditional perplexity (function-level ranking, then block-level knapsack) reaches **up to 5.6x compression without degrading** code completion, summarization or RepoQA. Single-turn only, not agentic. [abstract-verified] — [arXiv 2510.00446](https://arxiv.org/abs/2510.00446); code: [YerbaPage/LongCodeZip](https://github.com/YerbaPage/LongCodeZip) (license not verified). SWE-Pruner reports that PPL-based compressors such as LongLLMLingua "disrupt syntactic and logical structure" in agent settings [snippet] — [arXiv 2601.16746](https://arxiv.org/abs/2601.16746).
- **Context rot (Chroma, Jul 2025).** Across **18 models** (GPT-4.1, Claude 4, Gemini 2.5, Qwen3), reliability drops as input length grows, even on simple retrieval and replication. Needle–question similarity, distractors and haystack structure all have non-uniform effects. [vendor technical report] — [Chroma: Context Rot](https://www.trychroma.com/research/context-rot); code: [chroma-core/context-rot](https://github.com/chroma-core/context-rot).
- **Execution instability of compression.** One Aug 2026 study examines execution instability of context compression in long-horizon agents. I did not see its findings. — [arXiv 2608.06503](https://arxiv.org/pdf/2608.06503) (title only; not read).

### Inferences
- There are two families. **Removal of stale or duplicate state** (masking, CORVUS, AgentDiet "expired") cuts cost without accuracy loss. **Lossy compression of needed content** (minification, aggressive pruning, summarization) trades accuracy for tokens, or adds recovery turns.
- SWE-Pruner and CORVUS both report **fewer rounds** (18–37%), not just fewer tokens per round. That is the property that makes savings survive prompt caching. Per arXiv 2607.12161, any graph-indexer change should be judged on *turns* and *billed cost*, not raw tokens.
- For graph-indexer, the gap in the literature is that nobody uses a **code graph to decide staleness**, i.e. which earlier observations an edit invalidated. That is a cheap deterministic signal graph-indexer has and summarizers don't.

### Gaps
- Licenses for SWE-Pruner, AgentDiet, CORVUS, ContextSniper and the Complexity Trap repo were not verified.
- No study found measures observation masking or CORVUS inside **Claude Code** specifically, where the harness is closed. ContextSniper and arXiv 2607.12161 are the only Claude Code measurements.
- The full ACON and Chroma numbers for code tasks were not found.

## 3. Structured repository representations for agents (graphs, maps, skeletons, summaries, traces)

### Takeaway
Code graphs reliably improve **localization** and cut localization cost. When measured end-to-end on issue resolution in a strong agent, the **cost reductions are small (≈2–10%)** but resolve rates rise. That matches graph-indexer's ~15%. The one case of large whole-trajectory gains (FastContext, up to 60% tokens) comes from *delegating exploration to a separate small model*, which keeps exploration out of the main agent's prefix.

### Cited Findings
- **Code Isn't Memory (Jun 2026).** A structural codebase index inside a fixed harness with **Claude Opus 4.7**, 3 seeds, on SWE-PolyBench Verified and SWE-bench Pro. Arms: index on, index off, and an agentic-grep comparator. Result: **large localization gain, statistically separated resolve gain, no cost penalty per task, lower cost per solve**. With the index, **mean turns 28.3 vs 36.0** and **mean tokens 10.1k vs 14.0k** against OpenCode. [abstract-verified + snippet; unclear whether 10.1k is per turn or per task] — [arXiv 2606.22417](https://arxiv.org/abs/2606.22417). Ledger, audit script and results DB released (license not verified). *Usable?* **This is the closest published analogue to graph-indexer and the best experimental template:** within-harness ablation, cost per *solve*, leak audit.
- **Codebase-Memory (Mar 2026).** A tree-sitter knowledge graph over MCP covering 66 languages, with call-graph traversal, impact analysis and community detection. Across 31 repositories: **83% answer quality vs 92% for a file-exploration agent, at 10x fewer tokens and 2.1x fewer tool calls**. It matches or beats the explorer on graph-native queries (hubs, caller ranking) in 19 of 31 languages. **Code Q&A, not bug fixing.** [abstract-verified] — [arXiv 2603.27277](https://arxiv.org/abs/2603.27277); code: [DeusData/codebase-memory-mcp](https://github.com/DeusData/codebase-memory-mcp) (license not verified). *Usable?* Yes, as a direct competitor and benchmark. Its pattern (large savings on Q&A with some quality loss) mirrors graph-indexer's 55% Q&A result.
- **RepoAtlas (Sept 2026).** Training-free. It keeps an **evolving, budgeted view** of a task-relevant code-graph subgraph (**15 nodes / 20 edges**) chosen by lexical, semantic and trajectory evidence with personalized PageRank. It projects the subgraph as a visual topology plus a textual index and **refreshes it only when the agent's phase (Localize / Edit / Test) makes it stale**. On all 500 SWE-bench Verified instances with 3 models it **resolves 63.1% / 68.0% / 72.4%**, beating mini-SWE-agent, LocAgent and SeeRepo with the fewest input tokens and model calls. **Per-instance API cost drops by only 6.9% / 2.9% / 2.4%.** [abstract/snippet] — [arXiv 2609.16936](https://arxiv.org/abs/2609.16936). *Usable?* Yes. The phase-aware refresh ("stale view" detection) and the fixed node/edge budget translate directly. The cost numbers confirm that **graph views mainly buy accuracy, not cost, on bug fixing**.
- **SeeRepo (Jun 2026).** On-demand rendered visualizations of query-centred repository subgraphs. On the SWE-Rebench leaderboard, **Pass@1 25.45% → 26.36%, input tokens -34.89%, cost -9.6%**. On SWE-QA, **API calls -35.7% and cost -26.2%**. [snippet] — [LLM Agents Can See Code Repositories, arXiv 2606.14061](https://arxiv.org/abs/2606.14061). This is another case of a ~35% input-token drop becoming a ~10% cost drop on issue resolution, and it agrees with the cache-dominance finding.
- **FastContext (Microsoft, Jun 2026).** A separate exploration subagent (4B–30B specialized models, trained on reference trajectories with task-grounded rewards) that runs parallel tool calls and returns **file paths and line ranges only**. With Mini-SWE-Agent on SWE-bench Multilingual, SWE-bench Pro and SWE-QA: **resolve up to +5.5%, coding-agent tokens up to -60%**, with marginal overhead. [abstract-verified] — [arXiv 2606.14066](https://arxiv.org/abs/2606.14066); code: github.com/phil-hx/fastcontext_c (license not verified). *Usable?* Yes. Graph-indexer can be the deterministic "explorer" that returns *citations* (path:line ranges plus a one-line role), not code bodies. The saving comes from keeping exploration **out of the main prefix**.
- **LocAgent (ACL 2025).** A heterogeneous graph (directories, files, classes, functions, with contain/import/invoke/inherit edges) exposed through search/traverse tools. **Up to 92.7% file-level localization accuracy**, and a fine-tuned Qwen reaches results comparable to proprietary models at **~86% lower cost**. [abstract-verified] — [arXiv 2503.09089](https://arxiv.org/abs/2503.09089); code: [gersteinlab/LocAgent](https://github.com/gersteinlab/LocAgent) (license not verified). CoSIL reports LocAgent at **$1.26 per instance on Lite and $1.67 on Verified** [snippet] — [CoSIL](https://arxiv.org/abs/2503.22424).
- **CoSIL (ASE 2025).** LLM-driven iterative call-graph search with a module call graph and dynamic function call-graph expansion. **$0.04 per instance on Lite, $0.05 on Verified** (Agentless $0.03 / $0.05). Top-1 file-level localization **+2.9 to 34.6%** and function-level **+8.6 to 98.2%** on Lite. [snippet] — [arXiv 2503.22424](https://arxiv.org/abs/2503.22424); code: [ZhonghaoJiang/CoSIL](https://github.com/ZhonghaoJiang/CoSIL) (license not verified).
- **KGCompass.** A repository knowledge graph that links issues/PRs to code entities, with retrieval by graph traversal. **58.3% repair (SWE-bench Lite, single LLM), 56.0% function-level localization, ~$0.20 per repair.** [snippet] — [arXiv 2503.21710](https://arxiv.org/abs/2503.21710).
- **OrcaLoca.** Priority-scheduled agent search on a code graph with **distance-aware context pruning**. CoSIL reports that OrcaLoca underperforms it. [snippet] — [arXiv 2502.00350](https://arxiv.org/abs/2502.00350).
- **RepoGraph (ICLR 2025).** A line-level repository graph plugged into agent and agentless frameworks. It "reduces costs associated with managing the entire repository while achieving comparable or superior performance", and the extra token cost is justified by the gains. [snippet] — [arXiv 2410.14684](https://arxiv.org/abs/2410.14684). I recall a ~32.8% relative improvement on SWE-bench Lite [unverified / from memory].
- **Agentless (FSE 2025).** Hierarchical localization (files → classes/functions → edit lines) then diff repair. **32.00% on Lite at ~$0.70** (v1.5); **27.3% at $0.34 per issue** (v1.0). [snippet] — [arXiv 2407.01489](https://arxiv.org/abs/2407.01489); code: [OpenAutoCoder/Agentless](https://github.com/OpenAutoCoder/agentless). I believe it presents files in a compressed **"skeleton" format** (signatures without bodies) at class/function localization [unverified / from memory].
- **Code Graph Model (CGM, NeurIPS 2025).** Graph structure goes *into the model*: node attributes are mapped by an adapter, and **graph-aware attention** restricts attention to adjacent nodes. With an agentless Graph-RAG pipeline on **Qwen2.5-72B: 43.00% on SWE-bench Lite**, first among open-weight models and +12.33% over the previous best open-source method. [abstract-verified] — [arXiv 2505.16901](https://arxiv.org/abs/2505.16901). *Usable?* No: it needs fine-tuning and model-internal changes. See §6.
- **Meta Code World Model (CWM, 32B).** Mid-trained on **120M Python execution traces** (line-by-line state transitions) and **3M agentic SWE trajectories**. **SWE-bench Verified 53.9% (65.8% with test-time scaling).** [snippet; weights in three variants] — [arXiv 2510.02387](https://arxiv.org/abs/2510.02387); code: [facebookresearch/cwm](https://github.com/facebookresearch/cwm) (license not verified; I believe it is a non-commercial research license, unverified). *Usable?* Not as a model. The implication is that **execution state as representation** is valuable. Graph-indexer could supply cheap *observed* traces (test → covered functions, recorded values) as facts.
- **Aider repo map.** A tree-sitter map ranked by PageRank over the reference graph and fitted to a token budget. I found **no controlled measurement** of its effect on cost or success. — Gap.
- **Windsurf Codemaps, DeepWiki, CodeWiki, RepoAgent (hierarchical summaries).** No controlled measurements of agent cost or success were found this session. — Gap.
- **CodeNib (Jul 2026)** is a "multi-view data system for serving repository context to coding agents". Title only; results not seen. — [arXiv 2607.25431](https://arxiv.org/pdf/2607.25431).

### Inferences
- The evidence splits cleanly. **Q&A and localization: large savings (up to 10x tokens; 84–95% in exploration).** **End-to-end bug fixing: 2–10% cost, with resolve +1–5 pp.** Graph-indexer's 55% / 15% sits in this band. It is not a flaw in graph-indexer; it is the ceiling of "better localization" as a lever.
- The only large end-to-end token savings (FastContext -60%, CORVUS -9–50%, SWE-Pruner -39–44%) come from (a) **isolating exploration in a separate context** or (b) **changing the trajectory structure** (live views, rounds cut), not from better retrieval rankings.
- RepoAtlas's **phase-aware refresh** and **15-node / 20-edge budget** are concrete design parameters for a "compiled" working-set view.

### Gaps
- No measured study was found for program slicing as agent context, for callee-contract/specification summaries, or for test-to-code maps as a context primitive in SWE agents.
- No measured study of Aider repo map, Windsurf Codemaps or DeepWiki on SWE-bench cost was found.

## 4. Agent-computer interface (ACI) design findings

### Takeaway
The original SWE-agent ablations still hold: a bounded viewer (100 lines) beats both smaller windows and whole files, **summarized** search beats iterative search, and lint-on-edit helps. 2026 harness studies add that the effects are **model-conditional**. Structured tools help weaker models, while bash-only lets strong models batch edits and so saves turns.

### Cited Findings
- **SWE-agent (NeurIPS 2024), GPT-4 Turbo on SWE-bench Lite.** Full ACI **18.00%** vs shell-only 11.00% (+64% relative). **100-line viewer is best; 30 lines drops to 14.3% and full file to 12.7%.** **Summarized search beats iterative search by 6.0 pp**, and iterative search does worse than no search tool. Linting in the edit command adds **+3.0 pp**. [snippet, body text] — [arXiv 2405.15793](https://arxiv.org/abs/2405.15793); [ACI docs](https://swe-agent.com/latest/background/aci/). Code: SWE-agent (MIT license, from memory, unverified). *Usable?* Yes. Graph-indexer's outputs should behave like **summarized search**: bounded, ranked, with counts ("47 more callers — refine"). Symbol views should be bounded to about a function or 100 lines rather than whole files. The SWE-agent paper also ablated history processing, keeping only the last few observations in full; the exact numbers were not verified [unverified].
- **Harness design study (Sept 2026).** Structured tools support models with limited shell proficiency. **Bash-only enables capable models to combine multiple code modifications in a single tool call**, i.e. fewer turns. Planning trims repeated verification. [abstract-verified] — [arXiv 2609.20804](https://arxiv.org/abs/2609.20804).
- **Harness Engineering: a source-code study of eleven coding-agent systems (Sept 2026)** compares context-management designs in deployed agents. Findings not read. — [arXiv 2609.00006](https://arxiv.org/pdf/2609.00006) (title only).

### Inferences
- For frontier models (Opus/GPT-5-class), the ACI levers that cut *turns* are the ones that matter: batched multi-symbol reads, batched edits, and a single "run the relevant tests" command. A graph tool returning one fact per call is likely turn-inefficient.

### Gaps
- No 2025–2026 re-run of SWE-agent's window-size and search-summarization ablations with current frontier models was found.

## 5. Reducing reasoning and output tokens: do precomputed facts reduce thinking?

### Takeaway
Direct evidence is thin but consistent. Reasoning and output drop mainly **through fewer rounds** (SWE-Pruner: completion -40%, rounds -18–35%) and **less ambiguity** (clean code: reasoning -11%; full task spec vs bare story: -29.7% spend). Thinking budgets saturate early (8k→32k adds ~1.4 pp). Structuring *how* the model reasons (semi-formal certificates) raises accuracy, but no measured reasoning-token reduction was found. No study was found that injects precomputed types, callers or effects and measures reasoning tokens directly.

### Cited Findings
- SWE-Pruner cut **completion tokens by 40.8% (Sonnet 4.5) and 44.0% (GLM-4.6)** alongside round reductions of 18.3% and 34.6%. [snippet] — [arXiv 2601.16746](https://arxiv.org/abs/2601.16746).
- Cleaner code: **output -8.5%, reasoning characters -11.1%, revisits -33.8%**, pass rate unchanged. [snippet] — [arXiv 2605.20049](https://arxiv.org/abs/2605.20049).
- Full specification vs bare user story: **+29.7% token spend** for the bare story (Kimi K3, 3 effort levels). [abstract-verified] — [arXiv 2608.25399](https://arxiv.org/abs/2608.25399).
- Overthinking: reasoning models overthink more, and choosing lower-overthinking runs gives **~+30% performance and -43% compute**. [abstract-verified] — [arXiv 2502.08235](https://arxiv.org/abs/2502.08235).
- Thinking budget 8k/16k/32k gives **67.3 / 68.4 / 68.7%** on SWE-bench Verified (Claude 4 Sonnet). [snippet] — [arXiv 2512.10398](https://arxiv.org/pdf/2512.10398).
- **Semi-formal reasoning (Meta, 2026).** Forcing explicit premises, traced execution paths and formal conclusions (a "certificate") improves patch-equivalence accuracy **78% → 88%** (93% on real agent patches), gives **87% on RubberDuckBench** and **+5 pp Top-5** fault localization on Defects4J. Token effect not reported in the abstract. [abstract-verified] — [Agentic Code Reasoning, arXiv 2603.01896](https://arxiv.org/abs/2603.01896). *Usable?* Yes. If graph-indexer emits facts in **premise form** (e.g. "f is called by {g,h}; f raises X when …; covered by tests T1,T2"), the model can cite them as premises instead of deriving them in reasoning. This hypothesis is untested.
- Accuracy peaks at intermediate cost, and extra tokens often reflect "unproductive exploration or inefficient reasoning cycles". [abstract-verified] — [arXiv 2604.22750](https://arxiv.org/abs/2604.22750).

### Inferences
- The most plausible mechanism for cutting reasoning is to **remove open questions the model would otherwise reason about or verify empirically**: which tests cover this function, who calls it, what invariants callers rely on, whether a symbol changed since it was read. Each answered question saves an exploratory turn, which is where the cache-read cost is.
- Graph-indexer's post-edit phase (verification, tests, re-reading) maps onto **three precomputable facts**: (1) the impact set of the diff (callers and callees affected); (2) the minimal set of tests covering the changed functions (test-to-code map); (3) a fresh post-edit view of the changed symbols (CORVUS-style), so the agent doesn't re-open files. None of these has been measured in the literature.

### Gaps
- No controlled experiment was found where types, call graphs or effect summaries are injected and **reasoning tokens** are measured in a SWE agent. This is an open research gap and a publishable experiment for graph-indexer.
- No study was found on how test-to-code maps (targeted test selection) affect agent verification-phase cost.

## 6. "Revolutionary" lab-level approaches: learned representations, latent compression, KV reuse. Feasible for an external tool?

### Takeaway
Learned or latent representations (graph-aware attention, trained KV "cartridges", gist/soft tokens, execution-trace pre-training) show large gains in memory or accuracy but **all need model weights or serving-stack control**. None is usable with closed API models (Claude, GPT) from an external MCP tool. For an external tool, the only "KV reuse" available is **provider prompt caching**. The actionable version of "compiled context" is a **stable, cache-friendly prefix plus a small live working-set view**.

### Cited Findings
- **CGM:** graph-aware attention plus an adapter gives 43% on SWE-bench Lite with Qwen2.5-72B. It needs fine-tuning. [abstract-verified] — [arXiv 2505.16901](https://arxiv.org/abs/2505.16901).
- **Cartridges (ICLR 2026, Stanford/Hazy):** a small KV cache trained offline per corpus by "self-study" (synthetic conversations plus context distillation). It **matches ICL performance with 38.6x less memory and 26.4x higher throughput**, extends effective context (128k → 484k on MTOB) and composes at inference without retraining. Codebases are named as a motivating corpus. [abstract-verified] — [arXiv 2506.06266](https://arxiv.org/abs/2506.06266). *Usable?* Only with self-hosted open-weights models.
- **Limits of precomputed memory (Aug 2026):** on Llama-3.1-8B, both saved KV caches and trained compressions **degrade when assembled from separately prepared parts**, **stay current only through rebuilds costing a large fraction of full preparation**, and **ignore corrections served beside them depending on phrasing**. [abstract-verified] — [What It Costs to Compose, Rebuild, and Correct Precomputed Memory, arXiv 2608.30647](https://arxiv.org/abs/2608.30647). *Implication:* latent repo representations clash with the edit loop. Code changes every turn in bug fixing, so rebuild cost kills the benefit exactly in the phase graph-indexer needs to improve.
- **KV reuse and compression research (2026):** KV Packet (context-independent KV caching without recomputation), C²KV (compressed, composable KV reuse), Leyline (KV cache directives for agentic inference) and "End-to-End Context Compression at Scale". Titles only, not read. — [2604.13226](https://arxiv.org/abs/2604.13226), [2607.17715](https://arxiv.org/abs/2607.17715), [2606.01065](https://arxiv.org/pdf/2606.01065), [2606.09659](https://arxiv.org/pdf/2606.09659).
- **CWM:** execution-trace pre-training (120M traces) gives 53.9% / 65.8% on SWE-bench Verified at 32B. [snippet] — [arXiv 2510.02387](https://arxiv.org/abs/2510.02387).
- **Prompt-cache economics:** with caching, ~87% of Claude Code cost is cache traffic. Changes that invalidate the prefix (summaries, rewrites) can raise cost. [abstract-verified] — [arXiv 2607.12161](https://arxiv.org/abs/2607.12161); OpenHands condenser case [snippet] — [PR #6597](https://github.com/OpenHands/OpenHands/pull/6597). Anthropic prices cache reads at ~0.1x the base input price and cache writes at 1.25x (5-min TTL) [from Anthropic docs, from memory; not re-verified this session].

### Inferences (feasibility for graph-indexer, which cannot change the model)
- **Not feasible:** graph tokens or graph-aware attention (CGM), soft/gist tokens, Cartridges, and custom KV injection into Claude/GPT. These require weights or serving access. They become an option only if graph-indexer targets self-hosted open models (Qwen/GLM via vLLM/SGLang), and even then arXiv 2608.30647 shows rebuild and staleness costs under edits.
- **Feasible analogues:**
  1. **A cache-stable "compiled" prefix.** Emit a deterministic, budgeted repo digest (module map plus the issue-relevant subgraph, RepoAtlas-style ≤15 nodes) once, early, and never rewrite it. Every later turn then reads it at cache price.
  2. **An append-only delta protocol.** After edits, emit *small deltas* ("symbols changed: …; stale earlier reads: …; impacted callers: …; tests to run: …") instead of re-injecting views. This keeps the CORVUS benefit (no re-reads) without breaking the cache prefix.
  3. **Exploration isolation.** Graph-indexer answers exploration in a sub-context or subagent and returns only path:line citations (FastContext pattern).
  4. **Fewer-turn tool shapes.** Batch queries (multi-symbol read, "impact plus tests" in one call), since turns, not tokens, carry the cost.
- A plausible "radically different" representation within these constraints is a **per-task compiled bundle**: target functions plus callee contracts (signature, raises, side effects, return invariants from code and docstrings), caller call-sites, covering tests with their commands, and recent execution observations. It would be delivered once, cache-stably, then kept current through diffs. The literature supports each ingredient separately (localization gains, CORVUS live view, test/verification cost share, spec-completeness effect of -29.7%), but **no study measures the bundle end-to-end**.

### Gaps
- No evidence was found on whether Claude Code **subagents**, Codex or Cursor background explorers reduce main-agent cost in measured SWE settings. Only FastContext (mini-SWE-agent) was found.
- No data was found on xRAG or gist-token methods applied to repository-scale code for agents.
- Licenses and exact cache pricing were not re-verified this session.
